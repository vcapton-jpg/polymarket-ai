# Chantier #5 — Heuristic Score Validation & Calibration: Design

**Date:** 2026-04-24
**Status:** Draft (pending user review)
**Depends on:** chantier #1 (measurement foundations), chantier #2 (signal sourcing), chantier #4 (ranking tuning pattern)

## 1. Goal

Turn the current heuristic scorer from a hand-picked black-box into a
**decomposed, tested, and measurable** variant that can be benchmarked against
the 4 baselines shipped in chantier #1 and tuned offline against historical
outcomes.

The audit §6.1 flagged: *"poids arbitraires jamais validés sur held-out set"*.
Chantier #1 shipped the measurement infrastructure
(`SignalPrediction`/`SignalOutcome`, `VariantRegistry`, `brier_from_outcome`,
`wilson_ci95`, `simulated_pnl_eur`) explicitly to unblock this chantier.

**Success criteria:**
- Every weight in `HeuristicScorer` has at least one test asserting its
  contribution (monotonicity or zero-ing effect).
- `heuristic_v1` is registered alongside `baseline_*` and writes a
  `SignalPrediction` row at every scoring tick.
- A validation report compares `heuristic_v1` Brier/P&L/Wilson CI95 against the
  4 baselines on the ≥200 available short-horizon outcomes.
- A candidate weights config is produced by offline coordinate descent, gated
  on Brier improvement with CI-disjoint confidence.

**Non-goals (YAGNI):**
- No ML (gradient boosting, logistic regression, neural nets). Linear weighted
  sum stays.
- No re-design of `FeatureBuilder`. The bucket thresholds (freshness bands,
  liquidity bands, etc.) remain hand-coded — a future chantier if motivated.
- No automatic promotion of candidate weights. Tuner proposes, human reviews
  and merges.
- No change to `MIN_SIGNAL_STRENGTH=45` gate or `signal_score_threshold`. Those
  are orthogonal.

## 2. Architecture

Three layers, each independently testable:

**Layer A — Decomposition (code hygiene, zero semantic change):**
```
HeuristicScorer.compute_score(features)
  → strength_scorer.compute_signal_strength(features, weights)
  → trade_scorer.compute_trade_quality(features, weights)
  → weighted sum with STRENGTH_WEIGHT/TRADE_WEIGHT
```
Each sub-scorer is a pure function. Weights live in a frozen dataclass
`HeuristicWeights` loaded from `Settings`. No I/O, no logging — testable in
isolation.

**Layer B — Variant measurement (reuses chantier #1 infra):**
```
signal committed
  → record_baselines() writes one row per variant:
     - variant='heuristic_v1'      (frozen weights, always written)
     - variant='heuristic_shadow'  (Settings weights, opt-in via flag)
     - variant='baseline_*'        (existing 4 baselines, unchanged)
```
The `variant='signal'` write path in `app/measurement/pipeline.py::record_baselines`
is renamed to `heuristic_v1` (data migration 025 rewrites history so the names
stay consistent). Shadow prediction is computed inline in `record_baselines`
when `settings.heuristic_shadow_enabled=True` — it does **not** go through
`VariantRegistry.register_shadow` (that API is chantier #2's async sourcing
shadow, a different concern).

**Layer C — Offline validation + tuning (one-shot human workflow):**
```
scripts/validate_heuristic_weights.py      # rejoin predictions + outcomes
  ↓
docs/audit/heuristic_validation_report_2026-04-24.md

scripts/tune_heuristic_weights.py          # coordinate descent
  ↓
docs/audit/heuristic_weights_candidate_2026-04-24.json
  ↓ [manual review]
  ↓ [manual] update Settings defaults → re-run shadow → flip
```

**Tech stack:** Python 3.12, SQLAlchemy 2.0 async, Alembic, pytest-asyncio, no
LLM calls, no new external dependencies.

## 4. Layer A — Decomposition

### 4.1 `HeuristicWeights` (new)

```python
# app/scoring/weights.py
from dataclasses import dataclass, field

@dataclass(frozen=True)
class HeuristicWeights:
    # strength sub-scorer: freshness + source + confirmation + llm
    w_freshness: float = 0.15
    w_source: float = 0.10
    w_confirmation: float = 0.15
    w_llm: float = 0.60
    # trade sub-scorer: liquidity + spread + time_to_resolution
    w_liquidity: float = 0.40
    w_spread: float = 0.35
    w_time_to_resolution: float = 0.25
    # top-level combination
    strength_weight: float = 0.75
    trade_weight: float = 0.25

    def __post_init__(self) -> None:
        # Invariants checked at construction; raise ValueError on violation.
        s_sum = self.w_freshness + self.w_source + self.w_confirmation + self.w_llm
        t_sum = self.w_liquidity + self.w_spread + self.w_time_to_resolution
        top_sum = self.strength_weight + self.trade_weight
        for name, v in (("strength", s_sum), ("trade", t_sum), ("top", top_sum)):
            if abs(v - 1.0) > 1e-6:
                raise ValueError(f"{name}_weights sum to {v:.6f}, expected 1.0")

    @classmethod
    def load_from_settings(cls, settings) -> "HeuristicWeights":
        # Read heuristic_w_* overrides from Settings; fall back to dataclass defaults.
        return cls(
            w_freshness=getattr(settings, "heuristic_w_freshness", cls.w_freshness),
            # ... (enumerated at plan time)
        )

    @classmethod
    def frozen_v1(cls) -> "HeuristicWeights":
        """The snapshot used at chantier #5 launch — never touch."""
        return cls()  # relies on defaults being the v1 values
```

### 4.2 Sub-scorers (new, pure)

```python
# app/scoring/strength_scorer.py
def compute_signal_strength(features: dict, weights: HeuristicWeights) -> float:
    """Combine freshness + source + confirmation + llm into [0, 1]."""
    return (
        weights.w_freshness * features.get("freshness_score", 0.0)
        + weights.w_source * features.get("source_weight", 0.0)
        + weights.w_confirmation * features.get("confirmation_score", 0.0)
        + weights.w_llm * features.get("llm_strength", 0.0)
    )
```

Same shape for `trade_scorer.compute_trade_quality`.

### 4.3 `HeuristicScorer` refactor

```python
# app/scoring/heuristic_scorer.py
class HeuristicScorer:
    def __init__(self, weights: HeuristicWeights | None = None):
        self.weights = weights or HeuristicWeights.load_from_settings(get_settings())

    def compute_score(self, features: dict) -> dict:
        strength = compute_signal_strength(features, self.weights)
        trade = compute_trade_quality(features, self.weights)
        final = self.weights.strength_weight * strength + self.weights.trade_weight * trade
        return {
            "signal_strength": round(strength * 100, 2),
            "trade_quality": round(trade * 100, 2),
            "final_score": round(final * 100, 2),
        }
```

Public API unchanged. `derive_*_label` methods stay (they're just thresholds).

## 5. Layer B — Variant Registration

### 5.1 `predict_heuristic()` helper

```python
# app/measurement/heuristic_variant.py
from app.measurement.variant_registry import VariantPrediction
from app.scoring.weights import HeuristicWeights

def predict_heuristic(
    *,
    weights: HeuristicWeights,
    features: dict,
    direction: str | None,
) -> VariantPrediction:
    """Recompute a final_score under arbitrary weights and package it as a
    VariantPrediction.

    `direction` is inherited from the parent signal — the heuristic is
    direction-agnostic; it only scores strength/quality, not YES vs NO.
    `probability` maps the [0,1] final_score directly to P(move) for Brier
    scoring against t15min/t1h/t24h outcomes.
    """
    from app.scoring.strength_scorer import compute_signal_strength
    from app.scoring.trade_scorer import compute_trade_quality
    strength = compute_signal_strength(features, weights)
    trade = compute_trade_quality(features, weights)
    final = weights.strength_weight * strength + weights.trade_weight * trade
    return VariantPrediction(
        direction=direction,
        probability=max(0.0, min(1.0, final)),
    )
```

### 5.2 `record_baselines` rewiring

Current shape (chantier #1):
```python
rows = [{..., "variant": "signal", "predicted_probability": signal_prob, ...}]
for name, fn in registry.baselines().items():
    rows.append({..., "variant": name, ...})
```

Chantier #5 shape:
```python
# 1. Frozen reference: heuristic_v1 (replaces the 'signal' row).
#    Uses the same probability the Signal already carries — no recomputation needed.
rows = [{..., "variant": "heuristic_v1", "predicted_probability": signal_prob, ...}]

# 2. Opt-in shadow: heuristic_shadow (recomputed with Settings weights).
if get_settings().heuristic_shadow_enabled:
    shadow_pred = predict_heuristic(
        weights=HeuristicWeights.load_from_settings(get_settings()),
        features=sig.features,   # persisted on Signal; see §5.3
        direction=sig.direction,
    )
    rows.append({
        "signal_id": signal_id,
        "variant": "heuristic_shadow",
        "predicted_direction": shadow_pred.direction,
        "predicted_probability": shadow_pred.probability,
    })

# 3. Existing baselines unchanged.
for name, fn in registry.baselines().items():
    ...
```

The `variant='signal'` string is deleted from `pipeline.py`; migration 025
rewrites historical rows so the name is uniform.

**Features plumbing:** `record_baselines` needs the feature dict to compute the
shadow variant under Settings weights. Two options (plan picks one):
- (a) add a `features: dict | None = None` kwarg to `record_baselines` and have
  `SignalBuilder` pass the features it already computed during scoring, or
- (b) load features by joining `event_market_features` on
  `(event_id, market_id)` within `record_baselines`.

Preference: **(a)** — no extra DB round-trip in the hot path, and `SignalBuilder`
naturally owns the feature dict. Fallback to (b) only if the scoring flow
doesn't hold the dict at commit time (verified at plan time).

**Parameter space** (7 weights, respecting sum constraints):

| Weight | v1 | Grid | Notes |
|---|---|---|---|
| `w_freshness` | 0.15 | 0.05, 0.15, 0.25, 0.35 | strength bloc |
| `w_source` | 0.10 | 0.05, 0.10, 0.20 | strength bloc |
| `w_confirmation` | 0.15 | 0.05, 0.15, 0.25 | strength bloc |
| `w_llm` | 0.60 | derived = 1 - others (kept in [0.2, 0.9]) | strength bloc |
| `w_liquidity` | 0.40 | 0.2, 0.4, 0.6 | trade bloc |
| `w_spread` | 0.35 | 0.15, 0.35, 0.50 | trade bloc |
| `w_time_to_resolution` | 0.25 | derived = 1 - others | trade bloc |
| `strength_weight` | 0.75 | 0.5, 0.65, 0.75, 0.85 | top-level |
| `trade_weight` | 0.25 | derived = 1 - strength_weight | top-level |

Coordinate descent: 2 passes over
`[w_llm, w_liquidity, w_spread, w_freshness, strength_weight]` (free params;
the others are derived by the sum-to-1 constraint). ~30 evaluations total.

**Objective:** minimize `brier@t1h`. Tiebreak: maximize `simulated_pnl`.

### 6.4 Promotion gate (3-check)

For the candidate to be flagged "ready for manual promotion":

1. **Brier disjoint improvement:** `brier_candidate_ci95_high < brier_v1_ci95_low`
   (strict).
2. **P&L non-regression:** `pnl_candidate_mean ≥ pnl_v1_mean × 0.95`
   (tolerate 5% P&L slip for Brier gain).
3. **Per-label non-regression:** among the 3 signal buckets (low / mid / high
   via `derive_strength_label`), no bucket's Brier worsens by > 5%.

If gate fails → candidate JSON records `gate_status: "failed"` with
per-condition diagnostics. Script exits 0 (success = ran the analysis); gate
failure is a data finding, not a script error.

### 6.5 What promotion looks like (runbook sketch)

**Not implemented in this chantier** (YAGNI — we don't know yet if the tuner
will find a winner). If the tuner produces a passing candidate:
1. Human reviews `heuristic_weights_candidate_*.json`.
2. Edits `HeuristicWeights` defaults in `app/scoring/weights.py`.
3. Enables `heuristic_shadow_enabled=True` for 48h.
4. Re-runs `validate_heuristic_weights.py` on the new shadow data.
5. If shadow confirms offline finding → merge; update `frozen_v1` snapshot to
   new values for the next tuning cycle.

This runbook is written as a stub in
`docs/runbooks/promote_heuristic_candidate.md` as the final task.

## 7. Testing Strategy

### 7.1 Sub-scorer tests (Layer A)

For **each weight** in `strength_scorer` and `trade_scorer`:

```python
def test_freshness_monotone():
    """Higher freshness strictly increases signal strength, others equal."""
    w = HeuristicWeights()
    low = compute_signal_strength({"freshness_score": 0.0, ...}, w)
    high = compute_signal_strength({"freshness_score": 1.0, ...}, w)
    assert high > low

def test_freshness_zero_weight_zero_contribution():
    """w_freshness=0 → freshness has no effect."""
    w = HeuristicWeights(w_freshness=0.0, w_source=0.25, ...)  # adjusted to sum to 1
    s1 = compute_signal_strength({"freshness_score": 0.0, ...}, w)
    s2 = compute_signal_strength({"freshness_score": 1.0, ...}, w)
    assert abs(s1 - s2) < 1e-9
```

7 weights × 2 tests = 14 new tests (minimum). Plus sum-invariant tests.

### 7.2 Variant wiring tests (Layer B)

```python
def test_predict_heuristic_v1_weights_match_signal():
    """heuristic_v1 prediction is a round-trip of the Signal's own strength."""
    weights = HeuristicWeights.frozen_v1()
    features = _sample_features(freshness=0.8, llm=0.5, ...)
    pred = predict_heuristic(weights=weights, features=features, direction="BUY_YES")
    assert pred.direction == "BUY_YES"
    assert 0.0 <= pred.probability <= 1.0

def test_predict_heuristic_shadow_differs_when_weights_differ():
    """Shadow weights that differ from v1 yield a different probability."""
    features = _sample_features(llm=1.0)   # drive full llm contribution
    v1 = predict_heuristic(weights=HeuristicWeights.frozen_v1(),
                           features=features, direction="BUY_YES")
    shadow = predict_heuristic(weights=HeuristicWeights(w_llm=0.2, w_freshness=0.55,
                                                        w_source=0.10, w_confirmation=0.15,
                                                        ...),
                               features=features, direction="BUY_YES")
    assert v1.probability != pytest.approx(shadow.probability)
```

Plus an integration test: with `heuristic_shadow_enabled=True`,
`record_baselines()` writes 2 heuristic rows (`heuristic_v1` +
`heuristic_shadow`) alongside the 4 baselines; with flag off, only
`heuristic_v1` plus the 4 baselines.

### 7.3 Script tests (Layer C)

- `test_validate_heuristic_weights.py`: on a 20-row fixture (predictions +
  outcomes), assert Brier/P&L numbers match hand-computed values.
- `test_tune_heuristic_weights.py`:
  - Convergence: trivial synthetic data where best weights are known (e.g.

  - Gate rejection: candidate worse than v1 → `gate_status: "failed"`.

## 8. Risks & Mitigations

| Risk | Mitigation |
|---|---|
| 225 samples is thin for 7-weight tuning; CIs will be wide. | 3-check gate requires disjoint CIs; most candidates will fail → we learn "data insufficient" without hurting prod. |
| Migration 025 rewrites history; irreversible if we later find bug. | Downgrade restores `'signal'`; tested; dev DB backup before apply. |
| Shadow double-writes double write volume on `signal_predictions`. | `heuristic_shadow_enabled` defaults `false`; turned on only for 48h validation windows. |
| LLM scoring feature (`llm_strength`) is itself stochastic — weights tuned on noisy feature. | Out of scope; noted as future chantier. Validation report includes raw LLM-strength distribution for context. |
| Renaming `variant='signal'` → `'heuristic_v1'` breaks downstream dashboards/scripts. | `grep -r "variant.*signal"` at plan time; update every call-site in the same chantier. |

## 10. Out of Scope / Future

- Re-calibrating the `FeatureBuilder` bucket thresholds (freshness bands,
  liquidity bands, etc.) — a separate chantier when data volume warrants.
- Replacing the linear scorer with ML (GBM / logistic reg) — needs ≥10× more
  outcomes resolved.
- Bayesian calibration of `probability` output (currently naive
  `p = final_score`). Would warrant Platt scaling / isotonic once we have
  enough resolved outcomes.
- Long-horizon `price_resolved` validation (only 18 rows today; check back in
  2-3 months).
